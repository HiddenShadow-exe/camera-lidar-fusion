# Occlusion completion for a LiDAR + top-view RGB-D camera: full project documentation

> **Audience:** another LLM or engineer who has to understand, run, debug or extend this project without the original author.
> **Status:** results of run `work_v3` (5-fold scene-level CV, 31 real boxes). Everything below was produced with the scripts in `occ_pipeline/`.
> A short human-oriented summary is in `README.md`.

---

## 0. TL;DR

* **Problem.** A warehouse robot has a LiDAR (Robosense Airy, 96 beams) and an overhead RGB-D camera. When a box is partly hidden behind another object (the *occluder*) the LiDAR sees only the occluder's surface. We want to "complete" the hidden part of the box so that the occupancy grid is correct.
* **Live method (the thing being improved).** Fit an oriented box to the **camera** point cluster of the target only (traditional CV: top plane → min-area rectangle → extend down to floor). LiDAR rays that were blocked by the occluder are *extended* until they hit the front face of that box. The new points are *regenerated points*; they are voxelised (3 cm) into the occupancy grid. The LiDAR is never used to fit the box.
* **Problem with the live method.** The camera box is a few cm off (bias + per-box noise), so regenerated points land in the wrong voxels.
* **Our contribution.** A neural model that looks at the camera cluster and predicts **how far to shift each of the 6 faces** of the CV box (independent faces, both directions). The shifted box is used for ray extension. Trained on *all* candidate shifts scored against ground truth (GT), evaluated out-of-fold.
* **Baselines compared on the same final voxelised completion:** (1) traditional CV box, (2) best single constant shift, (3) a PointNet that directly regresses an OBB from the camera cluster (`train_obb.py`, trained on hand-labelled boxes), (4) the hand-labelled box itself (upper reference), (5) oracle = best shift in the grid (uses GT, ceiling).
* **Headline (run `work_v3`, 31 boxes, ≤1-voxel F1 incl. vertex):** CV 72.0 → PointNet 81.5 → ours 83.3 → manual label 89.2 → oracle 94.3. Exact-voxel F1: 28.6 → 33.0 → 36.3 → 42.4 → 55.5. Ours vs CV: **+11.3 pp [0.9, 21.6]** (significant); PointNet vs CV: +9.4 [−1.4, 21.2] (not significant); ours vs PointNet: +1.8 pp [−4.9, 8.2] (indistinguishable). PointNet trained on even-recording labels only.
* **Honest caveats:** 31 real scenes, one seed, fixed 60 epochs. Gain over a constant shift is small and not statistically established. The model sometimes ruins an already good box (see §9).

## 1. Data and conventions

### 1.1 Raw dataset layout (`dataset/`)
```
dataset/
  full occlusion boxes/      recording_01 … recording_NN   (6 scenes after pairing)
  occluded boxes/            …                              (20 scenes)
  partial occlusion boxes/   …                              (5 scenes)
  multi occlusion boxes/     …                              (EXCLUDED from the v3 run: multiple occluders)
  virtual boxes/             generated by make_virtual_pairs.py (training only)
  _cardboard box/            NOT a pair; directories starting with "_" are skipped everywhere
```
* Every `recording_XX/` has `recording_data.json` and `pointcloud_lidar.pcd`.
* **Pairing convention: odd recording = occluded scene, even recording = ground truth (GT) of the same scene with the occluder removed.** Scene key = `<category>/<NN>` with `NN = (recording_no + 1) // 2`. This key is identical in our pipeline and in `train_obb.py`/`dataset_augmentation.py`, so CV folds map 1:1.
* The json holds: LiDAR points, camera RGB-D point cloud / calibration (`cam_K`, `cam_R`, `cam_t`), and the manual label under **`3d_data_lidar.obb_3d`** (despite the name this is a hand-drawn box of the **camera** point cloud, i.e. free of shadowing; its coordinates turned out to be in the LiDAR frame, detected automatically by s9b).
* Real data in v3: 91 pairs → 31 real scenes/boxes used for evaluation + 60 virtual pairs; 93 target boxes in stage 0 (31 real-scene boxes + virtual ones) → 372 samples (87+6 originals ×(1+3 aug)).

### 1.2 Coordinate frames
* Everything is stored in the **LiDAR frame**: x forward, z up, floor at z ≈ −0.40 m (LiDAR height 0.40 m).
* Camera → LiDAR: `q = R (p − t)`, `R = R_yaw @ diag(1, −1, −1)`; the camera looks straight down; camera centre = `−R·t`.
* Box axes are the **columns** of `R` (Open3D convention). Faces move along their outward normal; `+` grows the box.

### 1.3 Virtual occluder pairs (`make_virtual_pairs.py`)
100 single-box recordings (no pair) are turned into pairs: the original scan = GT; a synthetic box occluder is placed between LiDAR and target and the blocked scan points are replaced by its surface (parameters: thickness, width, height, front distance, lateral offset, yaw, range noise). They are **training-only** (240 virtual samples in v3), never evaluated.

## 3. The shift grid (candidates)

* A candidate is `[lo_x, hi_x, lo_y, hi_y, lo_z, hi_z]` in cm: each of the 6 faces moves independently along its outward normal (+ grows). Per axis `n_k = 2·n_steps_k + 1` positions per face; per-axis pair index `j = a·n_k + b`, so `C_k = n_k²` pairs. Flat index `f = (j0·C1 + j1)·C2 + j2`.
* **v3:** `--step 0.03 --n-steps 4 --n-steps-z 2` → x,y: 9×9 = 81 pairs each (±12 cm), z: 5×5 = 25 (±6 cm) → **164,025 candidates**. (Previous run `n_steps 3`: 7×7×7×7×5×5 = 60,025, ±9/±9/±6.)
* Candidates making a box < 5 cm thick on any axis are invalid (NaN, masked).
* Model heads have sizes (81, 81, 25); `P(candidate) = P_x·P_y·P_z` (factorised).
* `--step` = 3 cm equals the voxel size; so shifts are whole voxels. Small residual mismatch can only come from the box-aligned grid origin.

## 4. Regeneration and scores (what "good completion" means)

1. For a candidate box, a LiDAR ray (origin O, direction d, measured range r) is **blocked** if it enters the box at `t_in > r + 3 cm`. Its regenerated point is `O + t_in·d` on the box's front face.
2. Points are voxelised at **3 cm, box-aligned** (voxel frame = CV box frame, so scores don't depend on world placement).
3. Sets: `P` = regenerated voxels, `G` = all GT voxels, `S` = GT voxels hidden by the occluder (the shadow; what has to be recovered).
4. Scores (1 = perfect):
   * `exact = |P∩S| / (|S| + |P∖G|)`
   * `tol` = same with ≤1-voxel cube tolerance (26-neighbourhood)
   * `graded = Σ w(d)` with weights by squared voxel offset: exact 1.00, face 0.61, edge 0.37, vertex 0.22, 2-straight 0.14, farther 0 (`--graded-sigma 1`, `--graded-radius 2`)
5. **Oracle** = argmax per sample (ties → smallest shift). **Regret** = oracle − chosen score.

## 5. Evaluation definitions

### 5.1 Methods (identical tables for all shift-based methods)
* **CV box** = shift 0. **Best constant** = one shift for all boxes, fitted on training folds only. **Model** = argmax of the predicted distribution, out-of-fold. **Oracle** = uses GT, ceiling. **Random** = expected score of a random valid candidate.
* Stage 9 adds **PointNet OBB** and **Manual label** as *boxes* that are fed through the same regeneration/voxelisation (not as shifts).

### 5.2 Cross-validation
Scene-level 5-fold (`--cv 5`): all augmented copies of a scene stay in the same fold; virtual samples are train-only; fixed 60 epochs, no epoch picking on held-out data (v3 log shows held-out regret fluctuating ±0.05 between epochs; the last epoch is used). 95 % CIs = bootstrap over scenes (2000 resamples).

### 5.3 Stage 8/9 cell classes
Every cell of one set is classified by the nearest cell of the other set: `exact | face | edge | vertex | >1 voxel`. **Precision side:** regenerated → GT (all G). **Recall side:** hidden GT (S) → regenerated. Tolerance levels are cumulative (exact; +face; +face+edge; +face+edge+vertex). P/R/F1 are means over boxes. Panel (e) of the figure (Hausdorff) is of limited use because the recall side includes hidden GT that is unreachable by any front-face regeneration.

### 5.4 Stage 9 extra metrics
Chamfer / Hausdorff distance (cm, capped 30 cm for chamfer), IoU of the box with the manual label (1 cm grid-sampling OBB IoU), paired F1 differences with bootstrap CI, worst boxes. `--voxel-size N` re-scores everything at another voxel size (disables oracle/constant/parity gates; output `stage9<tag>_vox<N>cm`).

### 5.5 Parity gates
`s9` recomputes exact/tol/graded for the shift-based methods and requires agreement with the stage-4 tables (v3: mean |diff| 0.0001). `s8` does the same.

### 5.6 Live-script protocol (NOT comparable)
`occupancy_tolerance_eval.py` evaluates the unchanged live pipeline in **world-aligned** voxels against the **full** GT object; our protocol is box-aligned and uses the hidden part S for recall. Numbers must not be mixed. Re-scoring our boxes in the live protocol is an open item.

## 6. Models

### 6.1 Shift model (stage 6, `s6_train.py`)
* Input: camera cluster (2048 points in the CV-box frame; 1024 random per step, 3 mm jitter) + 9-d context (LiDAR origin and camera centre in box frame, CV dims).
* PointNet encoder + context MLP, three heads (81, 81, 25), 1.09 M parameters, Adam lr 3e-4, wd 1e-4, batch 32.
* Loss `soft`: target `q ∝ exp(score/τ)`, τ = 0.05 over all valid candidates of the sample; KL between `q` and the factorised prediction. `--score graded` (used in v3) trains on the graded table; `tol|exact|mix` also exist; `--loss expected|ce` alternatives.
* Virtual-occluder samples are always training data (`--no-virtual` = ablation).

### 6.2 PointNet OBB baseline (`train_obb.py`, user's code, unchanged)
Canonical frame via min-area rectangle, residual prediction of centre/size/yaw, symmetric corner loss, units dm; trained on hand-labelled boxes (`dataset_augmentation.py` creates augmented copies with labels). `s9a` trains it per CV fold with our folds (60 epochs, batch 32, lr 1e-3, width 64, dropout 0.2, 1024 points) so that held-out scenes are never seen. Reads `*/*/*/recording_data.json` of `--aug-data`.
**Label caveat in the first v3 run (fixed afterwards, see §9b; the rerun gave slightly lower PointNet scores):** `dataset_aug_v3` was built without `--label-key`/`--n-synthetic` (0 synthetic samples), many odd-recording labels cover only 0–40 % of the camera points (272 of 806 samples have <80 % of points inside the label), only 31 scenes (24–25 per fold) were loaded (virtual scenes aren't), held-out IoU 0.47–0.59. Even-only rerun: 403 samples, held-out IoU 0.56–0.72, completion F1 81.5 (≤1 voxel); the baseline is limited by the small number of labelled scenes rather than by the odd labels.

### 6.3 Manual label
`s9b` reads `3d_data_lidar.obb_3d` from the even json (odd fallback only with `--allow-odd`), picks the label nearest to the camera-cluster centroid (≤0.25 m), tests LiDAR vs camera frame by cluster coverage (v3: all 91 in LiDAR frame, median 92 % of cluster inside label, bottom at floor ±5 cm). It is an upper *reference* (a human saw the unshadowed camera cloud), not a deployable method.

## 7. How to run (Windows PowerShell, `.venv`, CUDA)

Run **from the repo root** (`camera-lidar-fusion`), scripts live in `.\occ_pipeline\` and `.\model\` (running `python s7_evaluate.py` from the root fails with "can't open file"). Activate the venv first (`.\.venv\Scripts\activate`). Paths with non-ASCII characters (e.g. "Dávid") work but the console may garble them.

### 7.1 Exact commands of the `work_v3` run
```powershell
# stages 0-5 (augment, CV boxes, checks, score ALL candidates, pack). Stage 4 took ~57 min on GPU.
python .\occ_pipeline\run_pipeline.py --input dataset --work work_v3 --from-stage 0 --to-stage 5 `
       --n-aug 3 --voxel-size 0.03 --n-steps 4 --n-steps-z 2 --step 0.03 `
       --exclude-units occluded_boxes_07_u1

# stage 6: 5-fold CV, graded-score loss, 60 epochs (~5 min)
python .\occ_pipeline\s6_train.py --work work_v3 --cv 5 --epochs 60 --score graded --tag _graded

# stages 7, 8
python .\occ_pipeline\s7_evaluate.py            --work work_v3 --split cv --tag _graded
python .\occ_pipeline\s8_tolerance_breakdown.py --work work_v3 --split cv --tag _graded

# PointNet baseline: augmented, hand-labelled dataset, then per-fold training
python .\model\dataset_augmentation.py --input dataset --output dataset_aug_v3 --n-aug 12
#   (add --label-key / --n-synthetic 400 for a stronger baseline; note the flag is --n-aug, not --n_aug)
python .\occ_pipeline\s9a_pointnet_boxes.py --work work_v3 --pred work_v3/stage6/pred_cv_graded.npz `
       --aug-data dataset_aug_v3 --train-obb-dir model

# manual boxes, then the four-way comparison + paper figure
python .\occ_pipeline\s9b_manual_boxes.py --input dataset --work work_v3
python .\occ_pipeline\s9_compare_methods.py --work work_v3 --pred work_v3/stage6/pred_cv_graded.npz
```
**Why the augmentation step is needed before s9a:** `s9a` imports `train_obb.fit()`, which trains on `dataset_aug*/` (labelled, augmented samples); the pipeline's own stage-0 augmentation does not produce OBB labels.

### 7.2 Useful options
* Exclude bad units: `--exclude-units occluded_boxes_07_u1` (unit = `<pair slug>_u<k>`). Only label-based exclusion is advised (multi-occlusion category; the phantom unit); do **not** drop boxes because the CV box fails — that is the point of the method.
* Re-score at another voxel size: `s9_compare_methods.py --voxel-size 0.02` (and 0.04/0.05); other tolerance (`--tol-vox`) in the run_pipeline for stage 4.
* One-sample look: `python .\occ_pipeline\visualize_scene.py --work work_v3 --sample partial_occlusion_boxes_03_u0_orig000 --box=-3,0,0,0,0,0` (Open3D/matplotlib; shows CV box, oracle box, regenerated points, scores from the stage-4 table).
* Debug: `--only N`, `--smoke`, `--limit N`. Without the user's data, `make_synthetic_dataset.py` + `test_*.py` exercise all stages (no torch in that sandbox → stage 6/9a untested there except `--dry-run`).
* Seeds: `--seed` (stage 0/5/6, s9a). Different seeds are **not** run yet.

## 9. Known issues, diagnosis, and what to do next

1. **Over-correction of good boxes.** The model sometimes moves an already good box: v3 held-out per-sample regret model vs CV: `partial_03` 0.99 vs 0.12, `occluded_19` 0.47 vs 0.08, `occluded_13` 0.22 vs 0.04, `partial_06` 0.44 vs 0.36, `partial_02` 0.16 vs 0.12. Probable cause: the model chooses per-axis marginals independently (P = P_x·P_y·P_z), so a jointly bad combination (e.g. shrinking a face past the visible front) can be sampled by the argmax; the larger v3 grid (±12 cm) makes such combinations available and the 31 training scenes are few. *Not yet verified*: print the chosen shift of `partial_03` from `pred_cv_graded.npz` (`idx` → `ShiftGrid.decode`) and view it with `visualize_scene.py --box=...`.
2. **Fluctuating validation curve** (±0.05 regret between epochs, fold 1 barely beats CV: 0.144 vs 0.146). Single seed, fixed 60 epochs.
3. **23 % of oracle optima lie on the grid boundary** (was 29 % with n_steps 3) — the grid could still be larger, but the classification problem gets harder.
4. **PointNet baseline is small-data limited** (403 even samples, 24–25 scenes per fold, 0 synthetic). Held-out IoU with the label is 0.56–0.72, yet the completion F1 is no better than ours. Possible improvements not tried: `dataset_augmentation.py --label-key ... --n-synthetic 400`, more seeds, fine-tuning. One PointNet box lies outside the shift-grid reach (±12/6 cm), so some of its regenerated cells are not scored.
5. **Box-aligned scoring** differs from the live protocol (§5.6).
6. `s9b` prints "85/31" and `s9` "Manual label boxes for 85/31" because virtual samples are also read; cosmetic, evaluation uses the 31 common boxes.
7. Parked/open ideas: several seeds + ensemble (average predicted distributions), early stopping on an inner validation split, fall-back gating to the CV box when the model's confidence is low or the shift is large, yaw as a 7th shift, joint (non-factorised) head, z-flatness check (top/bottom faces barely influence the rays; best constant only moves z faces; "no z-flatness check for now"), re-scoring in the live protocol, per-category analysis, Hausdorff panel replacement (precision-side only).

## 9b. Label provenance: only EVEN recordings have a correct hand label
Only the **even** (ground-truth, occluder removed) recordings carry a correct manual box in `3d_data_lidar.obb_3d`. The label stored with an **odd** recording is the auto-computed visible-face box and does not fit the camera points (0–40 % of the points inside it).
* **Manual-label method (s9b):** reads the even json only (the v3 stage-9 table used even labels: the earlier `manual_boxes.csv` shows `source = even` for all rows). The odd fallback is now off by default (`--allow-odd`) and the script prints the label source counts.
* **Evaluation side of the PointNet baseline:** clean. Held-out boxes are predicted from the stage-0 camera cluster of the even recording.
* **Training side of the PointNet baseline (v3 run): contaminated.** `dataset_augmentation.py` and `train_obb.load_samples` read *every* recording, odd ones included, with their bad labels. That is the cause of the "272 of 806 samples <80 % inside label" warning. Expected consequence was a pessimistic baseline, which the rerun did not confirm. `s9a_pointnet_boxes.py` now drops odd-recording samples by default (`--use-odd` restores the old behaviour); **Rerun result (even only, 403 of 806 samples kept): PointNet ≤1-voxel F1 81.5 instead of 83.6, exact 33.0 instead of 33.4; ours − PointNet +1.8 [−4.9, 8.2]. The odd labels therefore did not hurt the baseline (the odd samples apparently acted as extra augmentation of the camera points); the conclusion stays: ours ≈ PointNet, both clearly above the traditional box, below the manual label. Final numbers in §8 use the even-only run.**

## 10. Gotchas for whoever continues
* The user's **live script must not be modified**; `occupancy_tolerance_eval.py` only imports it.
* Stage 4 is the expensive part (≈1 h GPU for 164 k candidates); everything after is fast. Changing `--n-steps/--step/--voxel-size` requires recomputing stages 4→9. Changing only the model/loss needs stages 6→9.
* `--force` is required to overwrite finished stages/folds; otherwise finished work is silently skipped.
* Scene keys are `<category>/<NN>`; names with spaces (`occluded boxes`) become `occluded_boxes` in sample ids. `occludedboxes/15` in a log is the console wrapping a line, not a different name.
* The sandbox used for development had **no torch and no user data**; stage 6/9a/s9 numbers were only produced on the user's machine. Test artefacts in the sandbox (`dataset_synth`, `work_*`) are not results.
* z up, floor −0.40 m, camera→LiDAR `R_yaw @ diag(1,−1,−1)`; if a gate about GT-to-box distance or the oracle score fails, suspect a frame/units mix-up first.
